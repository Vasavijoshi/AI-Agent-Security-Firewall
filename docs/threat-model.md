# Threat model

STRIDE-structured, then a dedicated agent-specific section — this is where the project's actual
threat surface lives, since STRIDE was designed for conventional client-server systems and doesn't
natively have a category for "the client is adversarial by design." Every control below names the
exact file and function that implements it. Where no real control exists, this says so explicitly
(`NOT FULLY MITIGATED`) rather than describing an aspiration as a fact.

Trimmed from `AgentFW_Architecture_v1.md` §17 the same way `docs/architecture.md` trims the rest of
that design — see `AGENTFW_CONTEXT.md` §1 for what's out of scope (Kubernetes, SPIFFE/SPIRE,
multicloud) and why this document doesn't threat-model infrastructure this repo doesn't build.

## STRIDE

| Threat | Affected asset | Attack scenario | Control | File / Function | Residual risk |
|---|---|---|---|---|---|
| **Spoofing** | Workload identity | A compromised or malicious container claims to be a different, more-privileged service (e.g. `admin_agent`) to get its policy charter. | `/attest` derives identity entirely from the caller's real source IP, cross-referenced against the Docker API — never from a self-asserted claim. A label (`docker run --label`) is attacker-settable; the Docker-reported image digest is not. | `identity/issuer.py` — `attest()`, `_lookup_caller_container()` | The container running `/var/run/docker.sock` (identity itself) has root-equivalent visibility into every container on the host, not just this project's — a real, accepted blast-radius trade-off (see README's Design decisions). Also: a script or process *inside* the correctly-attested container can still request tokens for whatever it wants to claim locally in its own printed output — this doesn't forge a real token, but see `docs/verification-log.md` Verification 5 finding 2 for how this created a real, documented reporting confusion in M3's own attack scripts. |
| **Spoofing** | Bearer token / stolen credential replay | An attacker who steals a valid token from one container tries to replay it from a different one. | The token carries `attested_ip`; the PEP compares it against the actual peer IP of the connection presenting it — a stolen token replayed off-box fails even with a valid signature. | `pep/pipeline.py` — `_verify_identity()` (the `claims.get("attested_ip") != peer_ip` check) | A token replayed from *within the same container* (e.g., by a compromised process sharing that container's network namespace) is not distinguishable from the legitimate caller — container-level compromise is not contained by this check, only cross-container replay is. |
| **Spoofing** | Deployed image identity | An attacker swaps a service's image for a malicious one with the same compose service label. | Trust-on-first-use digest pinning: the image digest observed on first successful attestation is pinned; every later attestation for that service must match or is refused. | `identity/issuer.py` — `attest()` (digest comparison); `identity/store.py` — `get_or_set()` | TOFU's named trade-off: whoever attests first wins the pin — an attacker who wins the race on first boot gets pinned instead of the real image (`tests/test_identity_issuer.py`'s own trade-off test names this explicitly). `EXPECTED_DIGEST_*` closes the window if configured; unset by default on a fresh clone. |
| **Tampering** | Request destination (confused-deputy via userinfo/encoding tricks) | `http://evil.com@trusted.com/`, percent-encoded traversal, homoglyph/punycode domains — crafted so what's evaluated differs from what's forwarded. | Canonicalize before evaluating, forward only the canonical form, never the original; idempotent (`normalize(normalize(x)) == normalize(x)`, invariant §3.6). | `pep/normalize.py` — `normalize_url()`, `normalize_path()` | Normalization covers the tricks this project's own test suite names (`tests/test_normalize.py`) — userinfo, percent-encoding, IDN/punycode, path traversal, duplicate query params, default-port folding. A normalization trick not in that set is, by definition, `NOT FULLY MITIGATED` until named and tested. |
| **Tampering** | Policy bundle integrity | A malicious or mistaken policy PR introduces a shadowed rule, an unknown role, or a structurally invalid bundle that silently changes enforcement. | The bundle is validated at build/deploy time — conflict/shadow detection, unknown-role/unknown-workload checks — and the PEP loads and compiles it once at process start, crashing loudly on a bad bundle rather than silently degrading. | `policy/compiler.py` — `compile_bundle()`; `pep/pipeline.py` (`BUNDLE, BUNDLE_WARNINGS = compile_bundle(...)` at import time) | The compiler catches structural problems (unknown workloads, missing `critical_path` coverage per role) — it does not catch a *logically* wrong but structurally valid rule (e.g., an overly broad `destination: ["*"]` a reviewer approves by mistake). Policy review remains a human control this repo can't automate away. |
| **Tampering** | In-flight event data | An attacker with network access to `eventstore` tries to alter a logged decision after the fact. | Events are appended, never updated, via a single-writer SQLite table; no update/delete route exists on `events/app.py`. | `events/store.py` — `write_event()`; `events/app.py` (no PUT/PATCH/DELETE `/events` route) | No cryptographic integrity (hash chaining, signing) on the event log itself — a party with direct filesystem access to the SQLite file could still edit rows outside the application layer. `NOT FULLY MITIGATED` against that specific threat. |
| **Repudiation** | "Which policy version allowed this?" | An operator needs to prove, after an incident, exactly which policy bundle and rule authorized (or denied) a specific action. | Every event carries `policy_bundle_version` and `policy_id` (the matched rule ID, or a default-deny sentinel) — durably logged before the action is released (log-or-deny, invariant §3.4). | `events/schema.json` (`policy_id`, `policy_bundle_version` fields); `pep/proxy.py` — `_build_event()`, `_log_event()` | Bundle versions themselves aren't independently signed or hash-verified in the event — a `policy_bundle_version` string that matches what's logged trusts the compiler's own versioning, not a cryptographic binding to bundle content. |
| **Repudiation** | "Did the PEP actually deny this, or did it never get logged?" | An operator can't distinguish "the PEP denied and logged it" from "the PEP crashed / the event never made it to the store" without container-log observability. | Every decision is echoed to the PEP process's own stdout *before* the durable-write attempt — `docker compose logs pep` doesn't depend on the eventstore being reachable (a real gap found and fixed via Docker verification, see `docs/verification-log.md` Verification 1). | `pep/proxy.py` — `_log_event()`; `pep/bypass_proxy.py` — `_log_bypass()` (same shared `"agentfw.pep"` logger) | None known beyond log rotation/retention, which this project doesn't manage — that's an operational concern outside a single-host demo's scope. |
| **Information Disclosure** | Secrets/PII riding inside an otherwise-allowed request | A structured secret (AWS key, JWT, PEM key, connection string, card/Aadhaar number) or high-entropy token is embedded in a request body a policy rule would otherwise ALLOW. | Regex + entropy detectors scan the request body when the matched rule sets `inspect: true`, the destination is external, or the tool is `agent.invoke`; findings narrow the decision (`BLOCK`→`DENY`, `REDACT`→`ALLOW_REDACTED`) via `min()` over the lattice. | `dlp/detectors.py` — `scan()`, `outcome()`; `pep/pipeline.py` (stage 5 gate and the `min()` narrowing in stage 7) | Regex/entropy detection is inherently incomplete — a secret that doesn't match a known structured pattern and isn't high-entropy (e.g., a plausible-looking but non-random internal password) is `NOT FULLY MITIGATED`. The entropy threshold (4.0 bits/char, `_MIN_TOKEN_LEN=20`) is a tuned heuristic, not a guarantee. |
| **Information Disclosure** | The DLP log itself becoming a secret store | Logging *what secret was found* would create a second, less-protected copy of the secret. | `scan()` returns detector name and severity only — never the matched substring; nothing downstream of it (event log, printed attack-script output) has access to the actual matched value. | `dlp/detectors.py` — `scan()` (returns `Finding(detector, severity)`, no matched text) | None identified for this specific threat — this is a clean, structural mitigation (there's no code path that could leak the value even by mistake, since the value is never captured past the regex match object). |
| **Information Disclosure** | Credential exposure to the agent itself | If the agent ever held the real credential for a downstream service, a prompt injection could exfiltrate it directly, with no firewall bypass required. | The agent never holds a tool credential. Short-lived Ed25519-signed identity tokens are the only thing minted to the agent; the PEP injects the real credential (where one exists) only after a policy check passes. | `identity/issuer.py` — `mint_token()` (via `identity/tokens.py`); `pep/proxy.py` — `_execute()` | Most tools in this project (`db.query`, `file.read`, `email.send`) have no real backend/credential yet — this control is validated in principle (the agent genuinely never sees a credential) but not yet exercised against a real downstream credentialed service. |
| **Denial of Service** | A single agent flooding the PEP or a downstream destination | A compromised or buggy agent issues many rapid calls. | `RATE_ANOMALY` scores rapid calls (`>5/60s`) into the risk factor vector, narrowing toward `RATE_LIMIT`/`QUARANTINE`; 5+ denials in 60s is also one of quarantine's automatic-entry triggers. | `risk/scorer.py` — `_is_rate_anomalous()`, `record_outcome()`; `pep/pipeline.py` (quarantine trigger block) | `RATE_LIMIT` is **NOT FULLY MITIGATED as throttling** — it currently executes the call exactly like `ALLOW` (README's decision-lattice status table). Only quarantine (a harder, all-or-nothing gate) actually stops anything; there is no soft per-agent rate cap. |
| **Denial of Service** | The bypass-catch listener as an amplification/resource vector | An attacker floods `pep/bypass_proxy.py`'s `:8081` listener with connections. | Each connection is handled with a 5-second read timeout and closed immediately after one denial response; no per-connection state is retained. | `pep/bypass_proxy.py` — `_handle()` | No connection-rate limiting on the listener itself — `NOT FULLY MITIGATED` against a high-volume flood, though the blast radius is bounded (the listener does no real work per connection, just denies and closes). |
| **Denial of Service** | Log-or-deny itself becoming a DoS vector | An eventstore outage denies *every* action, including entirely legitimate ones — availability sacrificed for auditability by design (see README's Design decision 1). | This is accepted, not mitigated — see the README's own "given up" framing. | `pep/proxy.py` — `tool_call()` (the `if not logged: ... DENY` branch) | This is a deliberate trade-off, not a gap, but it means the eventstore is a real single point of failure for the *entire system's* availability, not just its own. |
| **Elevation of Privilege** | A valid credential for the wrong identity/destination | A workload with a genuinely valid, correctly-signed, correctly-bound token tries to reach a destination or invoke another workload outside its charter. | Explicit-deny-first, default-deny policy resolution; east-west calls (`agent.invoke`) are matched on `(source_workload, dest_workload, action)`, a separate question from the main rule table, with the same default-deny-by-construction. | `policy/engine.py` — `evaluate()`, `evaluate_east_west()` | None identified for the mechanism itself (property-tested: `tests/test_invariants.py`'s "no implicit allow" invariant, and `tests/test_east_west.py`'s "valid credential, wrong identity, still denied" test) — but see the Agent-Specific section below for the identity-mismatch finding that complicates *verifying* this live for four of the nine M3 attack scripts specifically. |
| **Elevation of Privilege** | Taint ceiling bypass | An agent that ingested untrusted content (and is therefore tainted) tries to write or touch secret-class data anyway, hoping a specific rule's own conditions don't cover the tainted case. | A structural check, independent of any individual rule's own `session_taint` condition: `session_taint == "tainted"` unconditionally forbids `WRITE_TOOLS` or `max_data_class in {confidential, secret}`, regardless of what any rule declares (a rule author forgetting a taint condition can't accidentally open an exfil path). | `policy/engine.py` — `evaluate()` (the taint-ceiling block, distinct from per-rule `session_taint` matching in `_matches_taint()`) | The agent cannot set or clear its own taint bit (`pep/pipeline.py` sets it, never the caller) — property-tested as monotonic (invariant §3.5). No bypass mechanism identified. |

## Agent-specific threats

STRIDE's categories don't natively distinguish "the client is adversarial by design," which is
this project's actual premise. Named here individually, each still mapped to a real control.

| Threat | Control | File / Function | Residual risk |
|---|---|---|---|
| **Prompt injection (direct)** | Not detected at the text layer at all — out of scope by design (`docs/architecture.md`'s "Prompt injection containment, not detection"). Whatever the agent decides to do as a result is still mediated by the same 8-stage pipeline every other call goes through. | `pep/pipeline.py` — `run_pipeline()` (unconditional, no special-casing for "this call looks injected") | This is the project's stated thesis, not a gap: AgentFW does not claim to detect injection. If the resulting action falls inside the agent's charter and isn't tainted/DLP-flagged, it executes — containment bounds blast radius, it doesn't prevent a within-charter action taken under injected instruction. |
| **Indirect prompt injection** (the headline scenario, `A6`) | Any fetched content taints the session (`session_taint`), regardless of how trustworthy the source is rated — "an allowlisted domain is still someone else's content." The subsequent injected action is then evaluated under the taint ceiling and ordinary policy, same as any other call. | `pep/pipeline.py` — `run_pipeline()` (the `if tool == "http.get" and final_decision in EXECUTABLE_DECISIONS: _SESSION_TAINT[session_id] = True` block); `agent/providers.py` — `MockProvider`'s `m3_indirect_prompt_injection` script (demonstrates genuine compliance, not refusal) | `attacks/a6.py` demonstrates this concretely: the agent genuinely complies (fetches, then attempts a DB read and an exfil POST); the read is blocked by the role's own charter (not taint specifically, for `research_agent`), and the exfil POST is blocked by policy + taint + a threat-intel hit together. See `attacks/a6.py`'s own module docstring for exactly which mechanism does what — the project is explicit that this is defense-in-depth, not one clean causal chain. |
| **Tool abuse / malicious tool output** | A compromised or malicious tool result (not the initial fetch, but data returned from a *later* step) is treated as untrusted the same way a fetched page is — any `http.get` taints, regardless of what it returns. | `pep/pipeline.py` (same taint-setting block as above) | Only `http.get` sets taint. A malicious result returned via `db.query`/`file.read`/`email.send` (tools with no real backend yet — see Limitations) does not taint the session, since those tools don't currently execute real content-returning calls. This is a real, disclosed gap once those tools get real backends. |
| **Unauthorized destination access** (`A1`) | Default-deny: no matching rule means DENY, structurally, not by an operator remembering to add a catch-all. | `policy/engine.py` — `evaluate()` (`if not allow: return EvalResult(Decision.DENY, "DEFAULT_DENY", ...)`) | Property-tested (invariant §3.2, `tests/test_invariants.py`). No bypass identified at the policy layer; see network-layer bypass entries below for the separate, lower-layer version of this same question. |
| **Credential access / secret exfiltration** (`A2`, `A5`) | DLP catches structured secrets/PII in request bodies (stage 5); explicit policy rules deny credential-shaped resources outright for roles with no charter for them (e.g. `support_agent` and `hr_*`/`credentials` tables). | `dlp/detectors.py` — `scan()`; `policy/bundles/default.yaml` — `R-SUPPORT-003`, `R-RESEARCH-002`, etc. | `risk/scorer.py`'s dedicated `CRED_ACCESS` action-class factor (30 points, the highest of the four `ACTION_POINTS`) never fires in practice — `pep/pipeline.py`'s `ACTION_MAP` has no tool wired to the `cred_access` action class among the six real tools. Disclosed, not hidden: credential-access attempts are still stopped, just not via that specific risk factor. |
| **Lateral movement / east-west privilege escalation** (`A4`) | `agent.invoke` is matched on `(source_workload, dest_workload, action)`, separate from the main rule table; the default bundle's `east_west_rules` is empty, so every cross-agent call hits default-deny. | `policy/engine.py` — `evaluate_east_west()`; `policy/bundles/default.yaml` — `east_west_rules: []` | Verified locally (`tests/test_east_west.py`) and reached live over Docker (`docs/verification-log.md` Verification 5) — but the live result specifically showed `AGENT_QUARANTINED`, not `DEFAULT_DENY_EAST_WEST`, due to the quarantine-cascade finding. The mechanism itself is not in doubt (tested independently, locally); a *clean* live confirmation of this exact path from cold state is still open. |
| **Direct egress bypass / proxy bypass** (`A9`) | `HTTP_PROXY`/`HTTPS_PROXY` point at a catch-all listener that denies everything, loudly and attributably; `agent-net` being `internal: true` means even a request that ignores the proxy variables entirely has no network path out. | `pep/bypass_proxy.py` — `_handle()`; `docker-compose.yml` — `agent-net: { internal: true }` | This is the cleanest, most independently-confirmed result in the whole project: live-denied, attribution independently confirmed in `docker compose logs pep` (Verification 5), no caveat. |
| **URL normalization tricks / confused-deputy destinations** (`A8`) | See STRIDE's Tampering row above — same control, restated here for the agent-specific angle: an agent-supplied URL with userinfo tricks is normalized before evaluation and forwarding. | `pep/normalize.py` — `normalize_url()` | Covered for the trick classes this project's own test suite names; not proven exhaustive for classes not yet identified. |
| **Session taint abuse** | The agent cannot set, clear, or otherwise influence its own `session_taint` value — it is pipeline-owned state, not a request field the agent controls. | `pep/pipeline.py` — `run_pipeline()` (`_SESSION_TAINT` dict, keyed by `session_id`, mutated only by the pipeline itself); `pep/proxy.py` — `ToolCallRequest` (no taint field on the request model at all) | None identified — there is structurally no field or mechanism for a request to claim its own taint state. |
| **Malicious destination / tool use via threat intel** (`A7`) | Local O(1) blocklist lookup at stage 4, cheap enough to run before expensive inspection; a hit both scores heavily and independently triggers automatic quarantine entry. | `threat_intel/feed.py` — `is_known_bad()`; `pep/pipeline.py` (the `if ti_hit: quarantine.enter(...)` trigger) | The list is a two-entry local file with no external feed integration or update mechanism — `NOT FULLY MITIGATED` against any destination not already known to this static list. Named explicitly in Limitations. |
| **Workload impersonation** | See STRIDE's Spoofing rows — restated for the agent-specific framing: one compromised agent process pretending to be a *different* deployed agent. | `identity/issuer.py` — `attest()`, `_lookup_caller_container()` | Structurally prevented for cross-container impersonation (identity is IP-derived, not self-asserted). Same-container process compromise is not distinguished from the legitimate calling process — see the Spoofing row's residual risk. |
| **Image tampering / digest mismatch** | Trust-on-first-use pinning refuses any later attestation whose observed digest doesn't match what was pinned on first success. | `identity/issuer.py` — `attest()` (digest comparison against `identity/store.py`) | TOFU's race-window trade-off (see STRIDE's Spoofing row) — named and tested (`tests/test_identity_issuer.py`'s `test_tofu_trade_off_an_attacker_winning_the_race_gets_pinned`), not silently assumed away. |
| **Policy misconfiguration** | Build-time validation catches structural problems (unknown roles/workloads, missing critical-path coverage, conflict/shadow detection) before a bundle can be loaded. | `policy/compiler.py` — `compile_bundle()` | `NOT FULLY MITIGATED` against a structurally-valid but logically-wrong rule (e.g., an approved-by-mistake overly broad grant) — the compiler checks shape, not intent. Policy review remains a human control. |
| **Risk-engine false positives** | Every factor is capped (per-category and total) and fully explainable — `risk/scorer.py`'s `Factor` vector names exactly what contributed and why, so an operator can see *why* a benign call scored high rather than trusting an opaque number. | `risk/scorer.py` — `score()` | Measured, not assumed: the M3/M4 evaluation's own false-positive rate (0.0% on the benign corpus after two harness-bug fixes) and throttle rate (52.3%, `RATE_LIMIT` narrowing on cold-start novelty) are the concrete numbers — see README's Results table and Limitations for how seriously to weight them (corpus bias, synthetic clock). |
| **Risk-engine false negatives** | The risk score can only *narrow* a decision, never widen one past what policy already decided (monotonicity, invariant §3.1) — a false negative in risk scoring cannot override an explicit policy `DENY`, only fail to add additional scrutiny on top of an `ALLOW`. | `policy/engine.py` — the `min()` narrowing in `pep/pipeline.py`'s stage 7; `tests/test_invariants.py` (monotonicity property test) | A risk-engine false negative on a call policy would have allowed anyway still executes — risk scoring is a narrowing layer on top of policy, not a replacement for it, by design. This is the intended shape, not a gap, but it means risk scoring alone is never the last line of defense for anything policy hasn't already restricted. |

## What this threat model does not cover

Consistent with `AGENTFW_CONTEXT.md` §1's hard scope boundary: no Kubernetes NetworkPolicy,
no SPIFFE/SPIRE, no multicloud identity federation, no cloud-provider-specific IAM integration —
these are named as future direction in the README, not modeled here, because this repo doesn't
build them. This document also does not cover physical/host-level compromise (an attacker with
root on the Docker host can defeat essentially everything above) — that's outside any single-host
demo deployment's realistic threat model, and is true of every system built this way, not specific
to AgentFW.
